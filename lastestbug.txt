Critical bugs
1. Fake usage data drives the app, and the Flutter tick can fire limits that were never reached
- app_management_provider.dart:8-117 hardcodes usageMinutesToday values (Instagram 98, TikTok 124, and so on).
- limit_enforcement_service.dart:37-52 adds 1 to that number every minute while Lifelit is open, and it counts every restricted app, not only the one in use.
- The Screen Time screen, the totals and _fireAction all use this fake data.
- Instagram is already at 98 of 30 minutes, so the in-app fallback fires immediately when the accessibility service is off.
- The native service tracks real usage, but Flutter never reads it. The two sides disagree.
- Fix: expose real usage from the native UsageStatsManager through the method channel, and delete the simulation.
2. The daily limit can only be set up to 150 minutes
- updateDailyLimit clamps to 1–150, which is a product restriction. It is also the only place the limit is validated.
- Native code accepts any value, so the two sides can disagree if the stored config is edited.
3. Package matching is too loose, so unrelated apps get treated as managed apps
- LifelitAccessibilityService.kt:584 uses pkg.contains(it) || it.contains(pkg).
- isTransientPackage (line 119) and findLimitForPackage (lines 592-599) use the same pattern, and so does getRulesForPackage.
- A short or empty package name matches almost anything, because "x".contains("") is true.
- Example: "android" is excluded explicitly, but "com.google.android.youtube" contains "android". it.contains(pkg) can also match system packages.
- Threads (com.instagram.barcelona) contains instagram, so getRulesForPackage returns Instagram's rules for Threads.
- findHandlerForPackage then applies Instagram's handler to Threads. This is a real misclassification.
- Fix: use exact match against a package set, or startsWith for known aliases.
4. Twitter rules are stored under the wrong key
- getRulesForPackage maps Twitter to x_twitter, but falls back to activeRules["twitter"].
- The app id in Flutter is x_twitter, so the fallback is dead code and misleading.
- Any app that doesn't match the when gets Twitter rules through the fallback, because appKey is "" and the lookup of "" fails and then tries "twitter". Remove the fallback.
5. Time-limit blocking never turns off when the limit changes or the app is un-restricted
- loadLimitsFromPrefs returns early if there is no stored config (?: return). It does not clear activeLimits, so a stale limit stays alive.
- activeRules is overwritten by loadLimitsFromPrefs, but only when a feature is blocked (if (blocked.isNotEmpty())). If the user turns every feature off, the old rules stay in memory until syncRules clears them.
- syncRules is called on every save, so this mostly self-heals. It is still two sources of truth for the same data.
6. The block overlay is not touch-proof
- In showLimitIntervention the window uses FLAG_NOT_FOCUSABLE with MATCH_PARENT. The Back and Home gestures still work, and the user can leave to another app that has no limit.
- It also does not block the app from being relaunched. This is acceptable for a soft blocker, but the "Akses dikunci hingga hari berikutnya" message overpromises.
- A user can disable the accessibility service in Settings, and nothing detects or resists that.
7. The service can enforce a limit using mixed day boundaries
- systemUsageFor uses the device calendar at midnight, and todayKey() uses Date() with Locale.US. They agree on the device time zone.
- If the time zone or clock changes mid-day, tracked and system usage diverge, and maxOf keeps the larger one.
- ensureUsageDay clears lastInterventionAt but does not reset the cached lastSystemUsageMs. For up to 15 seconds after midnight it can still report yesterday's usage and wrongly block the app.
Logic and correctness problems
8. Tracked usage double-counts
- foregroundBaselineMs = max(tracked, systemUsage) is taken when a session starts. On session end the code stores max(tracked, baseline) + elapsed.
- The system value already includes time up to the session start, so this is mostly fine. The problem is that systemUsageFor is cached for 15 seconds, and UsageStats only commits when the app is paused.
- isTimeLimitExceeded takes max(tracked, system). While the session is live, tracked includes the baseline plus the live elapsed time. If UsageStats also commits mid-session after an app pause, the sum is not double-counted because max is used, but the baseline can be stale. In practice this is an approximation and not accurate to the second.
9. Foreground tracking runs on managed apps only and ignores the screen turning off
- updateForeground is only called when a managed app event arrives. Screen-off, lock, or a switch to an unmanaged app with no WINDOW_STATE_CHANGED event keeps the session open.
- The 15-second loop keeps adding elapsed time while the screen is off. The service never listens for ACTION_SCREEN_OFF.
- The result is that real usage is overcounted, and the user can be blocked unfairly.
- Fix: register a screen-off receiver and call updateForeground(null).
10. The Flutter service keeps its own copy of the "triggered today" state
- _triggeredToday is never reset automatically, because resetDailyTriggered() has no caller. After the first trigger, the limit never fires again until the process restarts.
- LimitEnforcementService.start stores the BuildContext in a long-lived Timer closure. If MainScaffold is disposed, stop() is called, so this is handled, but it is fragile.
- _showPopup and _showBlockedDialog use showDialog(context: context), which can use a stale context.
11. Notification-only mode (action 0) is silently suppressed
- canShowIntervention allows one banner per 60 seconds. That is intended.
- But enforceTimeLimit returns false for modes 0 and 1, so the code goes on to evaluate features. For popup mode (1), showFeedBlockOverlay is skipped while the popup is showing, which is correct.
- The popup can still be dismissed and will return 60 seconds later. This is consistent with the cooldown design.
12. Permission state is faked in several places
- screentime_screen.dart:117-118 calls toggleUsagePermission() and setUsagePermission(!hasPermission). This flips a boolean without the user granting anything.
- ScreentimeProvider._hasUsagePermission duplicates SettingsProvider._usagePermissionGranted, so there are two sources of truth.
- toggleOverlayPermission and toggleNotificationPermission flip local state only.
- _notificationPermissionGranted is hardcoded true, yet the manifest declares POST_NOTIFICATIONS and the app never requests it at runtime.
- Fix: read the real state from the native side and remove the toggles.
13. AppManagementProvider mutates model objects in place
- _apps[index].isRestricted = true and .dailyLimitMinutes = clamped mutate the object, while incrementUsage and _loadPersistentConfig replace it with copyWith.
- Mixing both styles makes the model unpredictable, and anything holding a reference to an old AppItem sees changes without a notification.
- The AppItem fields need to be consistently immutable or consistently mutable.
14. The "master toggle" logic only covers Instagram and TikTok
- dm_profile_only is a feature id that also appears in other apps' handlers. For apps other than Instagram and TikTok, toggling it only flips its own flag.
- Inside toggleFeatureBlock, TikTok's hide_stories and Instagram's hide_stories share an id, which is fine since they are scoped by app.
- There is a subtle problem with the Instagram master. constituentIds requires disable_friend_reels to be on for the master to activate. But disable_reels off forces the child off, and disable_friend_reels on forces disable_reels on. The state machine works but is hard to follow, and there are no unit tests for it.
15. Config load can crash and leave the state wrong
- _loadPersistentConfig casts appData['dailyLimitMinutes'] as int?. If the value was saved as a double, the cast throws.
- featMap[...] as bool has the same problem.
- The outer try/catch (_) swallows the error, so one corrupted entry discards the config for every app after it. The error is also not logged.
16. Hardcoded values and mixed languages
- isDark = true is hardcoded in every handler overlay call and ignores the theme setting.
- Overlay and native strings are hardcoded in Indonesian, while Flutter has an app_localizations.dart. The language setting does not affect native text.
- isDark ? const Color(0xFF1A1A1A) : const Color(0xFF1A1A1A) in _showSnackbar has two identical branches.
Architecture issues
1. Two sources of truth for config. Flutter holds the state, then writes JSON into native SharedPreferences, then sends a separate syncFeatureRules call. The native side parses both formats (activeRules from a ;/:/, string and from JSON). The delimiter format breaks if an app id or feature id ever contains :, ; or ,. Use one JSON blob and one load path.
2. Static mutable state in a service companion. activeRules and activeLimits are plain mutableMapOf shared across threads: the method channel runs on the main thread, and the service also runs on the main thread, so this works today. It is not thread-safe if anything moves to a background thread.
3. Business logic in a god class. LifelitAccessibilityService (721 lines) handles dispatching, usage tracking, persistence, limit enforcement, package matching and overlay orchestration. Extract a UsageTracker, LimitEnforcer and PackageMatcher.
4. Handlers keep state in instance fields (lastNavTimestamp) that are not reset on app switch or service restart.
5. Hardcoded app list in Dart. Adding an app means editing the provider, the manifest <queries> and the native handlers. Package aliases (TikTok musically and trill) are special-cased in MainActivity and again in the service.
6. getInstalledPackages returns all candidates on failure (return candidatePackages). If the channel call fails, every app is shown as installed.
7. Fragile selectors. View ids such as reel_watch_fragment_root and pivot_bar, and text matches such as "Beranda" or "Shorts", break with app updates and non-English locales. This is inherent to the approach and should be documented. A remote or updatable selector config would help.
8. ensureInitialized() is called inside onAccessibilityEvent after the early return for the app's own package, so some paths run before the handlers exist.
Android and manifest issues
- BIND_ACCESSIBILITY_SERVICE is declared with <uses-permission> in the app. This permission belongs only on the <service> element, and the extra declaration is unnecessary and can trigger lint warnings.
- PACKAGE_USAGE_STATS is correct, but there is no FOREGROUND_SERVICE or similar fallback. OEM battery killers (ColorOS, MIUI) will kill the process, and the Handler-based loop dies with it.
- The accessibility config listens to typeViewClicked|typeViewSelected and uses flagIncludeNotImportantViews. This raises event volume and battery cost. notificationTimeout=80 is also aggressive. canPerformGestures is declared but unused.
- The accessibility config has no packageNames filter, so the service receives events from every app and discards them in code. Scope it to the managed packages, with the TikTok aliases (com.zhiliaoapp.musically, com.ss.android.ugc.trill) included.
- The release build uses signingConfigs.getByName("debug"), so it is not ready for release.
- The Google Play accessibility policy needs a prominent in-app disclosure and a declaration form. Play may reject an app that uses the service to block other apps' features.
- The package is com.syacretary.lifelit but the Dart package is socialite. This is cosmetic and can confuse tests and imports.
- .idea, .claude, .cursor and .mimocode directories exist in the working tree. They are ignored by .gitignore or untracked, so no leak was found in git ls-files.
Test coverage gaps
- The only tests check rendering and restrict/unrestrict.
- app_management_test.dart calls the real MethodChannel without a mock. The failure is silently swallowed by catch (_), so the test passes without exercising the native path.
- There is no coverage for toggleFeatureBlock, config serialization or the limit math. The Kotlin side has no tests, and isTimeLimitExceeded, formatLimit, loadRulesFromPrefs and the package matching are all pure and easy to test.
Recommended fix order
1. Tighten the package matching (items 3 and 4), since it causes cross-app misbehaviour.
2. Handle screen-off and day rollover in usage tracking (items 7 and 9).
3. Remove the simulated usage and fake permission toggles, and read real data over the channel (items 1 and 12).
4. Replace the delimiter format with a single JSON config and clear stale state on load (items 5 and architecture 1).
5. Scope the accessibility service with packageNames and drop the unused flags.
6. Extract UsageTracker, LimitEnforcer and PackageMatcher, and add unit tests for them and for toggleFeatureBlock.
